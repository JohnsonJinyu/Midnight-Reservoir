# Midnight Reservoir · 午夜蓄能湖（频谱湖面壁纸）

可直接导入 **Wallpaper Engine**（Web 类型）的网页壁纸：紫橙发光的方块湖面（160×160 InstancedMesh + 自定义 GLSL），
上方是贴在同一块曲面幕布上的悬浮专辑卡与双行弧形歌词。歌词**纯本地 LRC，不依赖任何在线服务**。

## 运行 / 导入

- 浏览器预览：直接打开 `index.html`（左下角面板可调参数，按 `H` 收起；加 `?clean=1` 隐藏面板）。
- Wallpaper Engine：**把整个项目文件夹作为一个壁纸导入**——复制本目录到
  `Wallpaper Engine/projects/myprojects/` 下，重启 WE 后它会作为一张壁纸出现；
  或者 WE 里「创建壁纸 → 从文件夹导入」选中本目录。
  **关键：要让 WE 读到 `project.json`，不能只把 `index.html` 当散装网页文件拖进去。**
  只拖 `index.html` 的话，WE 会用一个裸 Web 壁纸条目接住它：标题变成 `index.html`、
  缩略图变成默认显示器图标、`project.json` 里的标题/封面/42→41 项属性面板**全部失效**——
  这正是「封面和名字都配好了却不显示」的根因。
  自检口径：**列表里应该是 `Midnight Reservoir · 午夜蓄能湖` + 发光湖面预览图；
  一旦看到 `index.html` + 显示器图标，就是导入方式错了，重新按文件夹导入。**
  正确导入后，属性面板是 `project.json` 定义的 41 项，按 5 组折叠：**音频律动 / 镜头与地形 /
  性能与画质 / 音乐信息卡 / 歌词**（配色常驻在最上面，不折进分组）。
  浏览器里想快速比对清晰度档位，加 `?res=hd|qhd|uhd`。
- 改动 `project.json` / `index.html` / 增删文件之后，先跑一遍自检：
  `node tools/validate-project.js`（漏字段、资源缺失、加载顺序反了都会直接报出来），
  动了属性面板再加一遍 `node tools/audit-props.js`。

### 改了 js 却看不到变化（踩过一次）

`webwallpaper64` 进程在**首次加载时就吃住了 DOM**，之后磁盘上的 js 改了它不会重新读 ——
桌面看起来「参数没生效」，其实是还在跑几分钟/几小时前那一份。

先确认工程路径没被复制：`wallpaper_engine/projects/myprojects/spectral-lake` 应当是指向本项目目录的
**符号链接**（`ls -la` 看箭头）。是链接就说明文件是实时的，问题只在进程没重载：

1. WE 主界面 → 已安装 → 右键这张壁纸 → **重新加载**；
2. 或者换成别的壁纸再换回来（等价于重新加载）；
3. 或者结束 `webwallpaper64` 进程（WE 会自己拉起来，屏幕会闪一下黑）。

判断有没有真的加载到新代码，最快的办法是看**卡片下沿有没有暖色渐变**：
bounce light 是 `pow(1−vUv.y, 2.6)`，只要加载到新版，深紫面板的下半部一定带暖色；
如果整块面板是均匀的死紫，那就是旧页面。

依赖顺序 = 上面自上而下的顺序，`index.html` 里就是按这个顺序 `<script>` 的。
没有构建步骤、没有模块打包（WE 用 `file://` 加载，ES Module 会被 CORS 拦），
所以模块之间靠**全局函数 + 明确的契约**通信，而不是 import。

### 七条必须守住的契约

1. **曲率只有一个来源**（`js/band.js`）
   `bandPatchGeometry(cx, w, h, rOff, seg, refWidth)`。任何新内容要贴到幕布上，都调这个函数，
   不要自己写 z 公式、也不要在画布上画假弧度。同一组内容必须传同一个 `refWidth`，
   否则封面和歌名会弯成两种弧度。

2. **字号用世界单位，不用画布像素**（`js/lyrics.js` 的 `LYRIC_TYPE` + `LYRICS_PPU`）
   历史坑：早期字号写的是「84px @ 1024 宽画布」，后来画布改成 2048、幕布加宽，
   字号没跟着改，屏幕上的字就悄悄变小、弧度也跟着消失 —— 表现为「改着改着视觉效果没了」。
   现在 `LYRIC_TYPE.active = 1.60` 是**世界单位**，画布像素只是换算结果，分辨率无关。
   另外：单行宽度还有一个显式上限 `LYRIC_MAX_W = 27`（世界单位）。长歌词靠
   `shrink` 自动缩字才放得下 —— 这个上限以前是「画布宽度」隐含给的（2048 ÷ 72 = 28.4 单位），
   结果长句会铺掉半个屏幕、而且 `歌词大小` 滑块对它几乎无效（缩字已经顶到上限）。

   **上限怎么选**（三个约束卡出来的区间）：

   | 约束 | 换算 | 允许的上限 |
   |---|---|---|
   | 画布可用宽 2028px ÷ PPU 72 | 28.17 | ≤ 28 |
   | 幕布留白 ×1.07 不超过画布 2048px | 2048÷72÷1.07 | ≤ 26.6（超出只是留白被压，不影响字号） |
   | `歌词大小` 拖到 1.3 时不缩字 | 27 → 13 字 | 越大越宽松 |

   取 **27**。实测「开始缩字」的门槛（中文全角字宽 ≈ 1em，按 `lyricMeasure` 的实际量宽）：

   | 字号 | 上限 22 时 | 上限 27 时 |
   |---|---|---|
   | 0.6 | 23 字 | 29 字 |
   | 0.9 | 16 字 | 19 字 |
   | 1.1 | 13 字 | 16 字 |
   | 1.3 | **11 字** | **13 字** |

   中文歌词一行多在 13 字以内，所以拖到最大时长句也能跟着变大，不再被压回去。
   16:9 下最长行约占屏宽 44%，4:3 下约 58%，两种比例都不会溢出画面。
   想再放宽必须同时提 `LYRICS_BASE_W`，否则会踩到画布宽这条隐藏约束。

3. **幕布宽度由文字宽度反推**
   歌词幕布宽 = 最长那一行 × 1.07。文字永远占满幕布，曲率就一定作用在文字上；
   如果幕布固定很宽、文字只占中间一小段，两端进深只有零点几，屏幕上就是一条直线（这就是「塌成平幕」）。
   **采样窗口必须走 uniform，不能用 `texture.repeat`**（这条坑吃得很贵）：
   three 的 `texture.repeat / offset` 只对**内置材质**生效。歌词和专辑卡用的是自定义
   `ShaderMaterial`，片元里写的是 `texture2D(uMap, vUv)` —— `repeat` 根本没人读。
   后果不是「窗口慢半拍」，而是**窗口压根不存在**：2048 宽的画布被整张拉满幕布，
   字的横向比例变成 `2048 ÷ 幕布宽`。幕布宽度只要一变（换句、短句接长句、下下句提前露头），
   字的横向尺寸与字距就跟着一起变 —— 屏幕上就是「这行字突然内缩一下、整体变短」。
   现在窗口是 `uUvScale / uUvOffset` 两个 uniform（`setPanelMapWindow` 写入），
   1 画布像素恒等于 1/PPU 世界单位，字号与幕布宽度彻底解耦。
   顺带修掉一个更早就在的观感问题：横向被压掉 40%（短句只剩 16%，直接压成一条竖线），
   方形的汉字全被压成长条 —— 这是「总觉得哪里不对」的来源之一。

   **宽度仍须与画布同帧更新，不许平滑**：窗口宽 = `bandW × PPU` 像素，这一帧最宽那行是
   `widest` 像素，窗口比它窄时字的两端会落在 UV [0,1] 之外被 `ClampToEdge` 切掉。
   只有**曲率**需要平滑：由单独的 `curveW` 驱动（0.45s 跟到目标），
   几何宽用 `bandW`、曲率参照宽用 `curveW`，两者解耦。
   宽度只决定「字在自身跨度内弯多少」（两端进深恒为跨度 × 12%）。
   两行之间的基线间距按**当前行字号**算（`CFG.lyricsGap`，默认 1.20 倍），不能按下一行字号算 ——
   下行字小近一半，按它算出来的基线间距比上行字还窄，两行必然贴在一起。
   单行超长时的缩字是**逐行**做的：整帧统一缩会让正在唱的那一行跟着下一句一起变小。

4. **像素密度只由两处决定**（`js/lake.js` 的 `renderPixelRatio()` + `js/lyrics.js` 的 `syncLyricsResolution()`）
   渲染分辨率档位管住 WebGL 后备缓冲的高度（1080/1440/2160，最多 2× 超采样），
   歌词画布再按同一个倍率重建 —— 字的**世界尺寸**不变，只是每单位塞进更多像素。
   所以「换档位只改清晰度，不改构图」；任何新增的 canvas 贴图都要照这个规矩挂上去。

5. **一块面板只有一套光学模型**（`js/panel.js`）
   专辑卡与歌词必须走同一个玻璃着色器（`makePanelMaterial`），否则两块内容摆在同一画面里
   会显出两种质感：一块像玻璃屏、一块像贴纸。颜色约定也钉死在这里：
   **所有颜色 uniform 按 sRGB 传，shader 里 `toLinear()` 解码，输出再 `toSrgb()` 编码** ——
   自定义 `ShaderMaterial` 不会自动插入 three 的编码转换，漏掉这一步颜色会整体偏灰。
   距离雾只有一处公式（`shaders.js` 的 `FOG_GLSL`），湖面和面板都 `#include` 它，
   否则两块内容就不在「同一团空气」里。

6. **`project.json` 顶层必须同时有 `type` 和 `file`**
   ```json
   { "type": "web", "file": "index.html", "title": "...", "preview": "preview.jpg" }
   ```
   少了 `file`，WE 找不到 web 入口，会**静默退回按 Scene 解析**：标题变成 `project.json`、
   缩略图变成显示器图标、类型显示「本地场景」、右侧面板冒出一堆场景默认项
   （音频监听 / 播放速度 / 翻转 / 图片筛选器 / 显示颜色选项），还会往工程里编译 `shaders/*.dxs`。
   表现看着像「歌词没了、属性没了」，实际跟渲染代码无关。跑 `node tools/validate-project.js` 可提前拦住。

7. **自定义 `ShaderMaterial` 不认 `texture.repeat / offset`**
   three 只给内置材质自动插入 `uvTransform`；我们片元里是自己写的 `texture2D(uMap, vUv)`。
   想「只取贴图的一块区域铺满这块面」，必须把窗口做成 uniform（`uUvScale / uUvOffset`，
   由 `setPanelMapWindow()` 写入），改 `texture.repeat` 是没有效果的 —— 而且它**不会报错**，
   只会安静地按整张画布铺满，把横向比例交给「面有多宽」去决定。
   歌词「换句时突然内缩、字距变紧」就是这个静默失效造成的（详见第 3 条）。

## 属性面板：分组与控件选择

### 分组机制（`type: "group"`）

`group` 是官方支持的特殊属性类型：**它之后的所有属性都归它管**，直到出现下一个 `group`。
所以「分组结束」不是靠闭合标签，而是靠**再写一个 group**；第一个 group 之前的属性不归属任何分组
（当前就是置顶常驻的「配色」）。`group` 只需要 `order` 和 `text`，不要写 `value`。

### 三类控件怎么选

| 控件 | 什么时候用 | 关键字段 |
|---|---|---|
| `combo` 下拉 | 档位有限、需要**可复现的精确值**（分辨率、清晰度、FPS 上限、配色） | `options[{label,value}]`，`value` 必须是字符串 |
| `slider` 滑块 | 需要连续调手感；步进由 `fraction` + `precision` 决定 | 见下方「滑块步进的坑」 |
| `textinput` 文本框 | **需要敲具体数字**、滑块给不准的项（歌词时间偏移 ms、磁盘路径） | `value` 用字符串；解析与兜底在 `props.js` 里做 |
| `bool` 复选框 | 纯开关 | `value` 必须是 `true` / `false`，不加引号 |

判据一句话：**能用「档」表达的就别给滑块，能量化到整数的就别给小数，能敲数字的就别让人拖。**

### 滑块步进的坑（一定要看）

官方文档原文：开了 `fraction` 才会出现 `precision`，**`precision` 默认 2，代表 0.1 的步进**。
也就是说步进 = `10^(2 - precision)`：

| `precision` | 实际步进 |
|---|---|
| 2（默认） | 0.1 |
| 1 | **1.0** ← 陷阱 |
| 0 | 10 |

所以「歌词大小 0.6–1.3 配 `precision: 1`」等于只剩 0.6 和 1.6 两档，滑块看着像坏了。
**WE 能做到的最细步进就是 0.1**，想要更细只能把数值域放大。

现在的做法：所有需要细调的滑块都改用**整数域**，最细再换算回实数。
`props.js` 用 `propScaled(v, scale, min, max, def)` 统一做除法，`project.json` 里看不到小数：

| 类型 | 域 | 换算 | 等效步进 | 例子 |
|---|---|---|---|---|
| 百分比型（强度/缩放/速度） | 40–300 之类 | `/100` | 0.01 | 歌词大小 60–130 → 0.60–1.30 |
| 位置型（高度） | -80–80 | `/10` | 0.1 | 专辑高度 12 → 1.2 |

属性 `text` 里带上 `（%）` 或 `（×0.1，10 = 1.0）`，用户看到 90 就知道是 90%。
`tools/probe-props.js` 会遍历每一个整数落点，确认没有跳档、没有重复。

### 当前的 5 组划分

| 分组 | 内容 | 调节方式 |
|---|---|---|
| （置顶，不分组） | 配色 | 下拉 |
| 音频律动 | 灵敏度 / 起跳 / 回落 / 低频展开 / 频率定位 / 波纹 / 顶面发光 / 静音呼吸 | 整数百分比（40–300 等） |
| 镜头与地形 | 仰角 / 水平角度 / 镜头距离 / 视野 / 地形范围 / 鼠标视差 | 整数（地形范围用整数百分比） |
| 性能与画质 | 渲染分辨率 / 渲染清晰度 / FPS 上限 | 全部下拉档位 |
| 音乐信息卡 | 只听音乐 / 显示卡片 / 卡大小 / 环绕 / 高度 / 歌名大小 / 待机光点 | 整数百分比、整数、×0.1 |
| 歌词 | 显示 / 大小 / 行距 / 弧度 / 高度 / 环绕 / **时间偏移（文本框）** / 署名 / 路径 / 诊断 | 整数百分比、×0.1、文本框 |

`props.js` 里所有数值入口都过 `propNum()`：combo 传的是字符串、文本框可能是 `-350`、
`−800`（全角负号）、`350ms`、全角数字 `１２０` 甚至空串，解析不出数字就退回默认值 ——
绝不让 `NaN` 流进 `CFG`，因为 `NaN` 在这些参数里是静默失效（不报错、动画直接不动）。
时间偏移额外做严格校验：认不出格式就归零，不做「猜数字」。

改过 `project.json` 之后跑三个自检，分工不同：

| 脚本 | 管什么 | 典型能拦住的问题 |
|---|---|---|
| `node tools/validate-project.js` | WE 能不能正确解析这份 `project.json` | 缺 `file` 被当成 Scene、`order` 重号断号、分组为空、资源缺失、脚本加载顺序反了 |
| `node tools/audit-props.js` | 面板上的控件是否真的接上了代码 | 属性定义了但 `props.js` 从不读（拖了没反应）、`CFG` 被赋值却没渲染代码消费、combo 默认值不在 options 里、condition 引用了不存在或非 bool 的属性、仍开着 `fraction` 的滑块 |
| `node tools/probe-props.js` | 「面板读数 → CFG 实数值」的换算有没有被改坏 | 整数档位跳档/重复、越界没夹住、脏输入漏进 `NaN`、旧属性 key 又被误读 |

### 标题长度

右侧面板宽度有限，`text` 超过约 20 个汉字宽就会折行、把控件挤下去。当前最长的一项是
「歌词弧度（%，0 = 平幕）」23 宽，其余都在 22 以内。写新属性时把解释放在括号里、一句话说完，
不要写成「（可选：放 .lrc 的目录，多个用分号分隔）」这种 50 宽的长句。

## 幕布曲面（物理含义）

```
z(x) = -(R - rOff) + x² / (2·Rc)      R = 40（距离），Rc 由「歌词弧度」滑块控制
```

中央最远、两侧朝观众卷过来 —— 相当于站在环形幕布内部靠前的位置。透视投影自动得到
「中间的字小、两端的字大」以及两头被拉高的弧线，不是画布上画出来的假弧。
`Rc` 按内容宽度归一（`Rc = refWidth / (8 × 0.12 × curve)`），所以短句不会因为只占幕布中间而变平。

## 光学：为什么这样才像真的

方向是「**偏光学**」：不把面板做成有边框、螺丝、厚度的实体屏，而是让**光的行为**符合物理，
面板本身保持轻盈。全部实现集中在两条着色器（`PANEL_FRAG` / `AURA_FRAG`）和 `panel.js` 的参数里。

| 现象 | 物理依据 | 实现 |
|---|---|---|
| 屏幕的「黑」不是纯黑 | 环境光在玻璃面上反射，黑位 = 环境辐照度 × 反射率 | `out = E·(1−F) + env·F`，E=0 时剩下 `env·F` |
| 越斜看反射越强、正看几乎透过去 | 菲涅尔（Schlick）：`F = F0 + (1−F0)(1−cosθ)^5`，玻璃 F0≈0.04 | 幕布是曲面，两端天生在掠射角上，边缘自动泛冷光 |
| 玻璃反光会跟着卡片起伏动 | 反射光看到的是下方发光湖面 | `reflect(-V,N).y` 朝下时反射更强 |
| 背面漏出一圈光 | 背光/LED 从玻璃边缘漏出，强度 ∝ 屏幕亮度 | 圆角 SDF 内边缘的 `exp` 衰减线（宽约 1.6% 面板高） |
| 亮的屏照亮周围空气 | 辐照度 ∝ 平均辐射亮度（**线性光通量**，不是感知亮度） | 封面缩到 32×32 量 Rec.709 亮度，再按 gamma 2.2 还原成光通量，驱动光晕与漏光（时间常数 0.6s） |
| 面板外围更暗 | 面板挡住幕布背后的光（AO），但内部仍有环境回弹 | 近黑带紫（不是 #000）的柔和外圈 |
| 远处的东西沉进霾里 | 大气透视：消光 + 入散射，趋向地平线色而非变透明 | 湖面与面板共用 `bandFog(d, range)`，雾从 34×range 起 —— 面板在 40 单位，几乎不受影响 |
| 屏有像素结构 | LCD/CRT 的扫描线 | 2%~3% 强度的正弦栅格，肉眼几乎看不出 |
| 下方湖面把光打到屏上 | 湖面是 y≈0 的发光面，面板挂在它上方：越靠下距离越近（1/r²）、光穿过玻璃还要被菲涅尔挡掉一部分 | `uBounceGain` 每帧按湖面能量写入，`(1−vUv.y)^2.6` 给下半部一条渐变，再加一条紧贴下沿的「下棱」高光；专辑卡全量、歌词 45%（没有玻璃底板可承接） |
| 封面与歌名是一块屏 | —— | D1：一整块衬板 + 一个圆角 + 一圈漏光，进度线共用 |

**为什么不做 Bloom / 景深**：要引入 `EffectComposer` 和额外两个 pass，4K 下像素成本翻倍，
和「性能开销」直接冲突。当前这条路线不新增任何 pass、不新增几何体，
16 次 draw call（其中 7 次是面板部件），帧开销与改造前基本一致。

一个刻意的取舍：**光晕不是 Sprite**。以前是一张永远正对相机的平面贴在半径 41.4 处，
跟曲面没关系；现在是把同样的圆角 SDF 贴到幕布曲面上（比面板大 k 倍，着色器按 k 把 uv 还原
到面板坐标系再算距离），所以光会跟着弧面铺开、随卡片起伏一起动。

### 光晕为什么会「突兀」，以及怎么收的

第一版参数（`spread 0.78` / `falloff 1.7` / 强度 `0.05+0.34·lum`）在**暗封面**上没问题，
一遇到米白这类高亮封面就翻车：铺到将近一个面板高的乳白光团，边缘还有一圈发光线框。
这里有两个独立的错误，都不是「调小一点」能解决的：

1. **驱动量用错了**。`lum` 是从 canvas 读出来的 sRGB 感知值，而辐照度正比于**线性光通量**。
   直接拿感知值驱动，等于把中灰（0.5）当成「有一半亮」，实际只有 22%；
   亮封面的差距被进一步放大。改成 `Math.pow(lum, 2.2)` 之后，中灰封面的光晕几乎消失，
   亮封面也不再失控。
2. **范围与衰减不成比例**。真实屏幕照亮周围空气是**近距离快速衰减**的，
   `spread 0.78` 意味着光能铺到 0.78 个面板高 —— 那是一团云，不是光。
   现在 `spread 0.30` + `falloff 3.0`（贴边最亮，约 0.3 个面板高就归零），
   贴片本身也只放到面板的 2.0 倍（0.78 / 3.6 时那 3.6 倍大的一块贴片只是给雾更大的活动空间）。
   再加 35% 的场景霾色（`uHazeMix`）压掉饱和度，因为空气散射不会让光保持原色。

边缘那圈「描边」是第三个原因：漏光带宽原来是 2.6% 面板高，加上光晕在 `d=0` 处正好是峰值，
两条亮带在边缘叠成一条实线。现在漏光收到 1.6%、强度减半，边缘变成柔和过渡。

**怎么判断「光晕还是太大」**：量一下截图里卡片右边缘往外的像素。卡片高 H 的话，
`0.3×H` 之内应该已经从峰值衰到背景色；如果一百多像素外还在 100/255 以上，
那多半不是参数问题 —— 是宿主还在渲染改动前加载的那份页面（见文末「改了文件看不到变化」）。

### 下方湖面打上来的光（bounce light）

湖面不是背景板，它是一片**发光面**，而专辑卡和歌词就挂在它上方 14 个单位的地方。
所以湖面亮起来的时候，两块内容的下沿应该被照亮 —— 这是它们「在同一个光源下」的证据，
也是之前画面最大的破绽：卡片像贴在暗处的一张图，跟下面那潭发光的湖完全不发生关系。

实现放在 `PANEL_FRAG` 的两个 uniform 上，光路拆成三件事：

| 因素 | 物理 | 代码 |
|---|---|---|
| 越靠下越亮 | 面板下沿离湖面近（1/r²） | `pow(1−vUv.y, uBounceFalloff)`，默认指数 **2.6** |
| 下沿的玻璃棱先被照亮 | 倒角/边框最直接地抓到这片光 | `smoothstep(0.88,1.0,down)` 的一条窄带（只给有真实边界的面板，文字层 `uShape=0` 不画） |
| 光要先穿过玻璃 | 菲涅尔反射掉一部分，透进去的才照到内容 | `× (1−F)` |
| 玻璃自身也映到这片光 | 反射方向朝下时才能看到湖面 | `× towardLake × F`（另加一项） |

指数**不能取太大**。第一版取 5 想让「只亮最下沿」更干净，结果 `pow(x,5)` 在 `x=0.5` 时
只剩 3%：面板高度 135px 时，真正有反应的只有最后 10px，肉眼看到的就是「一整块均匀的死紫」，
完全读不出下面有光源。取 2.6 之后渐变覆盖下半部约 60%，配上一条下棱高光，
即使卡片缩到 135px 高也能一眼看出光是从下面来的。

反方向的教训也在：`1/r²` 老实算出来的照度落到 +5/255 时，在暗场里人眼分辨不出来，
所以强度系数是刻意调大的（物理上正确的量级 × 2 左右）—— 这一项追求的是「读得出来」，
不是「数值精确」。

强度由 `lake.js` 每帧算：`0.05 + 0.42 × (0.14 + 0.58·lightEnergy + 0.18·glow + 0.08·idle)`，
安静时约 0.15、正常播放 0.25、鼓点爆一下到 0.45。颜色取主题的「峰值橙混暖核 58%」，
也就是湖面中央那块真正亮的颜色，而不是屏幕自己的主色。

**接触阴影的方向要反着来**：湖面越亮，被面板挡住的那块背景与周围的差越大，AO 应当**更明显**
（`0.26 + 0.26·lit`）。「湖面亮 → 影子变淡」是直觉但错的，那等于说影子被光填平了。

## 渲染分辨率档位

WE 没有现成的「分辨率」属性：网页壁纸的画布永远等于窗口大小。所以我们自己控制后备缓冲：

| 档位 | 效果 | 适用 |
|---|---|---|
| 跟随窗口（auto） | 1 CSS 像素 = 1 渲染像素 | 老行为，最省 |
| 1080p | 后备高度钉到 1080 | 4K 屏上 `dpr` 只有 0.5，弱显卡救命 |
| 2K / 1440p | 高度钉到 1440 | 1440p 屏或 2K 超采样 |
| 4K / 2160p | 高度钉到 2160（上限 2× 窗口） | 1080p 屏做超采样 / 4K 屏原生 |

「渲染清晰度」滑块是在档位之上再乘 0.75–2 的微调量。两者相乘后夹在 0.5–2.0，
保证任何组合都不会把显存打爆（25600 根方块 + 长片元着色器，像素量是线性成本）。

## 歌词来源（纯本地，无网络请求）

```
手动路径 lyricsfile
  → lyrics/_index.json 三重比对命中（同步器生成，见下）
  → lyrics/ 里的同名文件
  → 用户歌词文件夹 lyricsdir（分号分隔多目录）
  → localStorage 历史缓存
  → 都没有就留空（只显示专辑卡）
```

**整个壁纸不发任何歌词网络请求**——没有在线 API、没有兜底匹配、不依赖第三方服务。
好处是离线可用、不会因某天接口挂掉就废掉功能；代价是本地没有的歌就不会显示歌词，
需要自己把 `.lrc` 放进 `lyrics/` 或用「歌词文件夹」属性指定。

### 为什么用本地缓存（QQ 音乐）

同名不同曲是这里最容易翻车的点：「`你像风一样出现`」有原唱版和一堆 DJ 翻唱版，
按歌名从网上匹配极易显示成另一首歌的词。本地缓存就是播放器此刻显示的那份，
不存在串歌。

壁纸本身是网页，**没法列目录、也读不到工程外的文件**（WE 的 file 处理器只放行工程目录），
所以由工程外的 Node 脚本解密再落进来：

```
node tools\sync-lyrics.js           一次性同步（或双击 同步歌词.bat）
node tools\sync-lyrics.js --watch   常驻，每 20s 增量同步（双击 歌词同步-常驻.bat）
node tools\sync-lyrics.js --dir <路径>  缓存不在默认位置时手动指定
```

`tools/qq-qrc.js` 是纯 Node 的 QRC 解码器（无第三方依赖），链路实测为：

```
QMC1 异或（PRIVKEY 128 字节循环）→ 去掉 11 字节头 → QQ 专用 3DES → zlib 解压 → QrcInfos XML
```

其中 3DES 是 QQ 自己改过的 DES（S 盒笔误、15 轮加半轮、末轮不交换左右半边），
**标准库的 3DES 解不开**，所以实现了内置版本。解出来的逐字时间轴会被压成标准 LRC。

同步器产出：

| 文件 | 作用 |
|---|---|
| `lyrics/<歌名> - <歌手>.lrc` | 标准 LRC（逐行时间轴，去掉逐字标记） |
| `lyrics/_index.json` | 每条含歌名 / 歌手 / 时长，供壁纸按「歌名+歌手+时长」三重比对挑选 |
| `lyrics/.sync-state.json` | 增量用的 mtime+size 记录，避免每次重解全部文件 |

纯音乐条目（`此歌曲为没有填词的纯音乐`）不入 .lrc，只在索引里打 `j:1`，
壁纸看到就显示「纯音乐」。

本地索引靠「歌名 + 歌手 + 时长」三重比对防止串歌：歌名必须对得上，歌手按分隔符拆开逐个比
（「整名相等」或「两边都 ≥4 字且互相包含」），再参考时长——`群星` 这类合辑写法例外，
只认歌名完全一致。任一项明显对不上就当没找到，不显示错的歌词。

## 已知限制

- WE 只转发**当前那一个**系统媒体会话。若它转发的恰是暂停的腾讯视频，JS 拿不到正在播放的歌名，
  这时只能选择「什么都不显示」（`只显示播放中的音乐` 开关就是干这个的），没有别的办法。
- WE 的 `file` / `directory` 属性只支持图片视频，本地 `.lrc` 只能走 `textinput` + XHR；
  `file://` 下读本地文件可能被浏览器拦，这时歌词留空——不会退回在线（已彻底移除在线歌词）。
